# GitHub App : tout ce que vous pouvez réaliser avec ChatGPT ou Claude, sans GitHub Copilot

Cartographie fonctionnelle et technique — 21 octobre 2026

## 1. Ce qu'est réellement une GitHub App et jusqu'où elle peut aller

Une GitHub App peut devenir le centre de commande technique d'une plateforme de développement, de gouvernance, d'automatisation et de coordination de plusieurs agents IA. Elle n'a absolument pas besoin de GitHub Copilot pour accomplir ces fonctions.

Vous pouvez utiliser ChatGPT, Claude, d'autres modèles d'IA ou même des programmes classiques pour piloter l'App.

La distinction est importante :

- ChatGPT ou Claude analyse les demandes, raisonne sur le code, propose des solutions, prépare des modifications et peut appeler les outils qui lui sont accessibles.
- La GitHub App constitue l'identité technique qui accède aux ressources GitHub et exécute les opérations autorisées.
- Votre moteur d'orchestration organise les agents, les tâches, leurs responsabilités, les sessions et les autorisations.
- GitHub conserve les dépôts, le code, les commits, les issues, les PR, les contrôles et les traces associées.
- Votre infrastructure exécute les tâches qui nécessitent des ressources externes : analyse IA, compilation, tests, bases de données, serveurs ou déploiements.

Une GitHub App peut agir indépendamment d'un utilisateur sur les ressources de ses installations autorisées. Elle peut aussi agir au nom d'un utilisateur lorsque celui-ci lui donne les autorisations nécessaires.&#x20;

## 3. Développer et modifier automatiquement des logiciels entiers

C'est la première grande capacité à exploiter avec ChatGPT et Claude.

Une GitHub App autorisée peut notamment :

- Lire l'arborescence complète d'un dépôt et retrouver ses fichiers.
- Récupérer le contenu du code et les configurations.
- Lire et comparer des commits historiques.
- Identifier les branches, leurs divergences et les fichiers modifiés.
- Créer des fichiers, modifier des fichiers existants et supprimer des fichiers.
- Créer des commits associés aux modifications.
- Créer des branches de développement.
- Ouvrir des pull requests.
- Lire les commentaires et les demandes de changement.
- Ajouter des commentaires de revue et soumettre des reviews.
- Mettre à jour une PR après un retour ou un échec de validation.
- Demander une fusion, lorsque les permissions et les politiques GitHub le permettent.
- Préparer des opérations de restauration ou de retour à un commit antérieur.

Avec un modèle IA, vous pouvez transformer ces opérations techniques en missions complexes.

Exemple :

Vous demandez à ChatGPT :

> Analyse le dépôt, retrouve son architecture actuelle, identifie pourquoi les tests de l'API échouent, corrige les fichiers concernés sans modifier les autres fonctionnalités, crée une PR et fournis un rapport comparant les résultats avant et après correction.

Le processus peut devenir :

Demande utilisateur

Lecture du dépôt et des règles

Analyse par ChatGPT ou Claude

Préparation et modification du code

Tests et vérification anti-régression

Création et mise à jour de la PR

Validation, fusion autorisée et preuves

Cette chaîne peut fonctionner sans Copilot. Il faut simplement que l'orchestrateur puisse appeler les API de ChatGPT ou Claude et les opérations GitHub nécessaires.

Attention : une GitHub App ne garantit pas à elle seule la correction d'un bug ni l'absence de régression. Ces résultats dépendent du code produit, des tests exécutés et des contrôles indépendants.

## 4. Utiliser ChatGPT et Claude simultanément sur un même projet

C'est l'une des architectures les plus intéressantes pour votre objectif.

Vous pourriez créer différents agents, chacun avec une identité stable et un rôle déterminé.

| Agent           | Moteur possible         | Responsabilité                                    |
| --------------- | ----------------------- | ------------------------------------------------- |
| ARCHITECT       | ChatGPT ou Claude       | Étudier l'architecture et proposer les évolutions |
| CODER           | Claude ou ChatGPT       | Modifier le code dans le périmètre attribué       |
| REVIEWER        | Modèle distinct         | Examiner les changements du codeur                |
| TESTER          | IA + runners            | Concevoir, exécuter et examiner les tests         |
| SECURITY        | IA + scanners           | Évaluer les risques de sécurité                   |
| AUDIT           | ChatGPT ou Claude       | Vérifier les preuves et la conformité             |
| SUPERVISOR      | ChatGPT ou Claude       | Coordonner les missions et arbitrer les états     |
| AUTO-INTAKE/BUS | Service d'orchestration | Recevoir et distribuer les événements et demandes |
| DEPLOYER        | Agent outillé           | Préparer et réaliser les déploiements autorisés   |
| DOCUMENTATION   | IA                      | Maintenir spécifications, décisions et historique |

Un même agent logique pourrait même changer de fournisseur IA, sans perdre son identité documentaire.

Par exemple, une tâche commence avec Claude, mais sa prochaine session est exécutée par ChatGPT. Si l'historique, le mandat et les checkpoints sont persistés dans votre plateforme, la reprise peut utiliser cet état canonique.

L'élément essentiel est que l'identité de l'agent ne dépende pas du modèle IA employé.

GitHub propose également une catégorie particulière d'« Agent Apps », actuellement décrite comme une fonctionnalité en préversion publique. Toutefois, son intégration aux interfaces d'agents GitHub s'appuie sur des mécanismes associés à Copilot cloud agent. Puisque vous ne souhaitez pas utiliser Copilot, je ne recommande pas de construire votre architecture autour de cette intégration spécifique. Une GitHub App classique, pilotée par votre propre orchestrateur ChatGPT/Claude, suffit pour les workflows que vous voulez maîtriser.&#x20;

## 5. Construire une usine logicielle automatisée

Une GitHub App peut devenir le point d'entrée d'une véritable chaîne industrielle de développement.

Vous pourriez concevoir un système dans lequel une demande de fonctionnalité entraîne automatiquement la création d'un plan, l'attribution des tâches, la préparation du code, l'exécution de tests et l'ouverture d'une PR.

### 5.1. Le cycle complet possible

| Étape | Opération                                         | Acteur                           |
| ----- | ------------------------------------------------- | -------------------------------- |
| 1     | Recevoir une demande ou une nouvelle issue        | Webhook GitHub                   |
| 2     | Identifier le projet et son état courant          | Orchestrateur                    |
| 3     | Lire les règles et décisions du dépôt             | Agent documentaire               |
| 4     | Décomposer le travail en tâches                   | ChatGPT/Claude                   |
| 5     | Analyser les dépendances techniques               | Agent architecte                 |
| 6     | Réserver une tâche à un agent identifié           | Moteur de gouvernance            |
| 7     | Préparer une branche de travail                   | GitHub App                       |
| 8     | Générer et modifier le code                       | Agent codeur                     |
| 9     | Produire les tests                                | Agent testeur                    |
| 10    | Lancer les workflows CI/CD                        | GitHub Actions                   |
| 11    | Récupérer les résultats de tests                  | GitHub App                       |
| 12    | Corriger les erreurs détectées                    | Agent codeur                     |
| 13    | Contrôler les différences                         | Agent reviewer                   |
| 14    | Exécuter les contrôles de sécurité                | Scanners et agent sécurité       |
| 15    | Soumettre les modifications                       | Pull request                     |
| 16    | Collecter les approbations requises               | Gouvernance                      |
| 17    | Fusionner lorsque les conditions sont satisfaites | GitHub App ou personne autorisée |
| 18    | Déclencher un déploiement admissible              | CI/CD                            |
| 19    | Vérifier les services après déploiement           | Tests d'exploitation             |
| 20    | Enregistrer le résultat et les preuves            | Mémoire canonique                |

Une grande partie de ce cycle peut fonctionner de manière automatique, mais sa fiabilité dépend de mécanismes complémentaires : gestion des conflits, tests, règles de fusion, approbations, contrôles de coûts et reprise après incident.

GitHub permet notamment à une GitHub App ayant `Actions: write` de déclencher un workflow configuré pour `workflow_dispatch`.&#x20;

### 5.2. Exemple pour vos applications boursières

Imaginons une demande concernant votre application BRVM :

« Ajouter un nouvel indicateur financier aux fiches d'actions, sans modifier les calculs existants. »

Le système pourrait analyser le dépôt, identifier les composants d'affichage, les services de calcul et les tests, puis proposer une répartition entre architecte, codeur et contrôleur.

La GitHub App gérerait les commits, les PR et les vérifications.

L'analyse financière et la validation des formules seraient réalisées par des agents spécialisés, disposant de référentiels de calcul appropriés.

Une fois les contrôles satisfaits, la publication pourrait être préparée par le système de déploiement. La production resterait soumise à vos règles d'autorisation.

Cela peut fonctionner aussi bien avec ChatGPT qu'avec Claude.

## 6. Piloter tout GitHub Actions et les automatisations CI/CD

Avec les permissions appropriées, une GitHub App peut notamment :

| Fonction                              | Possibilité                            |
| ------------------------------------- | -------------------------------------- |
| Lire les workflows                    | Oui                                    |
| Créer ou modifier leurs fichiers      | Oui, avec permissions adaptées         |
| Déclencher manuellement des workflows | Oui                                    |
| Relancer certains workflows ou jobs   | Oui                                    |
| Annuler certaines exécutions          | Oui                                    |
| Consulter les runs et leurs états     | Oui                                    |
| Récupérer les logs disponibles        | Oui                                    |
| Consulter les artefacts               | Oui                                    |
| Supprimer des artefacts autorisés     | Oui                                    |
| Gérer certains paramètres Actions     | Oui                                    |
| Administrer les secrets Actions       | Oui, sans en lire les valeurs en clair |
| Gérer les variables Actions           | Oui                                    |
| Gérer les runners accessibles         | Oui, avec permissions appropriées      |
| Superviser les déploiements           | Oui                                    |
| Publier des checks                    | Oui                                    |
| Publier des statuts de commit         | Oui                                    |

Vous pourriez également construire un système d'optimisation des workflows :

- Identifier les jobs qui échouent régulièrement.
- Détecter les étapes CI/CD lentes.
- Examiner les changements ayant précédé les échecs.
- Comparer les performances des pipelines.
- Rechercher les tests instables.
- Proposer des changements de dépendances.
- Préparer des corrections des fichiers YAML.
- Identifier les actions GitHub tierces obsolètes.
- Vérifier les permissions demandées par les workflows.
- Contrôler les règles d'utilisation des runners.

Les fonctionnalités effectivement disponibles dépendent des API, du type de runner et de la configuration GitHub Actions.

Avec un moteur IA, vous pouvez aller plus loin : lorsqu'un workflow échoue, ChatGPT ou Claude peut recevoir automatiquement les logs pertinents, diagnostiquer l'échec puis ouvrir une PR corrective. Une telle correction doit toutefois passer par les contrôles normaux.

## 7. Administrer et gouverner les dépôts GitHub

Les droits administratifs permettent des opérations qui dépassent largement le développement.

Vous pouvez envisager l'administration centralisée des dépôts, par exemple pour :

- Créer et configurer de nouveaux repositories.
- Configurer les descriptions, pages d'accueil et paramètres exposés.
- Gérer les collaborateurs et certaines autorisations.
- Paramétrer des branches et règles de protection.
- Configurer des rulesets.
- Gérer les paramètres de fusion des pull requests.
- Encadrer les suppressions et modifications sensibles.
- Modifier les paramètres disponibles des fonctionnalités GitHub.
- Gérer certaines configurations de sécurité.
- Gérer les webhooks.
- Configurer les secrets et variables.
- Gérer les environnements de déploiement.
- Contrôler les informations d'archivage et de visibilité autorisées.
- Vérifier et éventuellement corriger les écarts de configuration.

### Une fonction particulièrement utile : contrôler des centaines de dépôts

Supposons que vous vouliez imposer les mêmes exigences à tous les dépôts d'une organisation :

- Aucun commit direct sur `main` sans autorisation appropriée.
- Une PR pour les changements nécessitant une revue.
- Des checks CI obligatoires.
- Une politique de sécurité commune.
- Des fichiers documentaires obligatoires.
- Une structure de traçabilité.
- Des vérifications avant fusion.
- Une politique de versionnement.
- Un dispositif de déploiement contrôlé.

L'App pourrait examiner les dépôts accessibles, détecter les différences de configuration et préparer leur harmonisation.

Vous pourriez également configurer certains rulesets avec des exceptions spécifiques pour des intégrations, lorsque GitHub prend en charge ces acteurs et leurs modes de contournement. Mais donner une exception à l'App elle-même doit rester une décision explicite : cela réduit les garanties fournies par la protection concernée.&#x20;

## 8. Créer une mémoire canonique et une continuité entre ChatGPT et Claude

C'est un des usages les plus importants pour une plateforme multi-agents.

GitHub fournit déjà des éléments persistants :

- Les commits et leurs identifiants SHA.
- L'historique Git et les différences entre révisions.
- Les issues et leurs commentaires.
- Les pull requests et leurs reviews.
- Les workflows et leurs résultats conservés.
- Les releases.
- Les fichiers documentaires versionnés.
- Les liens entre tâches, branches et changements.

Cependant, GitHub ne fournit pas automatiquement une mémoire sémantique universelle pour toutes les conversations ChatGPT et Claude.

Il faut donc créer une couche de continuité.

### 8.1. Ce qu'elle pourrait enregistrer

| Objet            | Informations persistées                      |
| ---------------- | -------------------------------------------- |
| Identité d'agent | Identifiant stable, type, rôle, capacités    |
| Session          | ID, début, état, agent, moteur IA            |
| Mandat           | Objectif, dépôt, ressources, limites         |
| Tâche            | ID, dépendances, priorité, responsable       |
| Checkpoint       | État de progression et preuves               |
| Décision         | Proposition, justification, approbation      |
| Historique       | Opérations effectuées et résultats           |
| Permissions      | Droits réellement vérifiés                   |
| Next action      | Prochaine opération admissible               |
| Handoff          | Transmission entre agents et sessions        |
| Incident         | Erreurs, blocages, investigations            |
| Livrable         | Commits, PR, artefacts et rapports           |
| Source canonique | Référence précise de l'état faisant autorité |

Une mémoire canonique utile doit pouvoir répondre à des questions telles que :

« Quel agent a créé cette branche ? »

« Quelle décision a conduit à cette PR ? »

« Pourquoi cette tâche est-elle bloquée ? »

« Quel checkpoint était valable avant l'incident ? »

« Quel modèle IA a réalisé les dernières modifications ? »

« Quels tests ont réellement été exécutés ? »

« Quel est le prochain travail autorisé ? »

« Quelles opérations ont été préparées mais jamais effectuées ? »

### 8.2. Votre système de reprise pourrait fonctionner ainsi

Nouvelle conversation ChatGPT ou Claude

Résolution de l'identité existante

Agent, projet, périmètre, session et source canonique

Reconstruction de l'état

Décisions, checkpoints, tâches, événements, commits, NEXT_ACTION

Vérification des autorités runtime

Droits effectifs, mandat valide, conflits et opérations admissibles

Reprise de la mission

Aucune nouvelle identité concurrente si une identité valide existe

Cette architecture serait compatible avec plusieurs fournisseurs IA. Elle ne dépendrait pas de leur mémoire interne.

Pour obtenir une continuité réellement fiable, les événements et transitions doivent être enregistrés pendant les opérations. Il n'est pas possible de reconstruire parfaitement, après coup, des pensées, décisions ou actions qui n'ont jamais été persistées.

## 9. Transformer GitHub en système de gestion de projet multi-agents

Vous pouvez créer un dispositif qui combine GitHub Issues, Projects, les labels, les commentaires et un moteur d'orchestration.

Il pourrait notamment :

- Recevoir de nouvelles demandes.
- Les classifier automatiquement.
- Déterminer le dépôt concerné.
- Identifier les fonctionnalités impactées.
- Rechercher les tâches existantes pour éviter les doublons.
- Décomposer un objectif en tâches techniques.
- Définir leurs dépendances.
- Identifier les opérations bloquantes.
- Proposer leur ordre d'exécution.
- Attribuer chaque tâche à un agent admissible.
- Produire et maintenir des issues.
- Créer des liens entre issues et PR.
- Mettre à jour des champs GitHub Projects.
- Surveiller les validations.
- Détecter des tâches abandonnées ou bloquées.
- Préparer des reprises de mission.
- Produire des rapports d'avancement.

### Exemple de structure possible

Un projet pourrait être organisé ainsi :

PROGRAMME — Plateforme universelle d'agents

BLOC 01 — Identités

Agents, sessions, utilisateurs, mandats

BLOC 02 — Communication

AUTO/BUS, événements, files et accusés de réception

BLOC 03 — Mémoire

Checkpoints, historique, décisions, reprise

BLOC 04 — Exécution

Code, tests, revues, PR et CI/CD

BLOC 05 — Gouvernance

Permissions, approbations, supervision

BLOC 06 — Exploitation

Observabilité, déploiements, incidents

Il est possible de créer automatiquement ces structures et leurs liens, mais il faut distinguer deux mécanismes : GitHub peut stocker les tâches et leur statut, tandis que la réservation exclusive d'une tâche par un agent, les transitions atomiques et le contrôle de concurrence doivent être gérés par votre moteur.

## 10. Gérer la sécurité de l'ensemble des projets

Une GitHub App disposant des droits appropriés peut participer à un programme de sécurité couvrant plusieurs dépôts.

| Domaine             | Possibilités                                            |
| ------------------- | ------------------------------------------------------- |
| Dependabot          | Consulter et traiter les alertes de dépendances         |
| Code scanning       | Consulter et gérer les alertes d'analyse statique       |
| Secret scanning     | Traiter les alertes relatives aux secrets exposés       |
| Security advisories | Gérer les avis de sécurité autorisés                    |
| Secrets Actions     | Créer, remplacer ou supprimer les secrets               |
| Dépendances         | Examiner les manifests et versions                      |
| Supply chain        | Contrôler les provenance attestations et artefacts      |
| Branch protection   | Vérifier les règles de protection                       |
| Workflows           | Examiner les permissions et risques des automatisations |
| Collaborateurs      | Auditer les accès exposés par les API                   |
| Rulesets            | Vérifier les politiques de branche et de dépôt          |
| Incidents           | Ouvrir, relier et suivre des issues correctives         |

Une architecture multi-agents permettrait d'attribuer la correction et sa vérification à deux agents distincts.

Par exemple, Claude propose un correctif, ChatGPT l'analyse, les outils de sécurité l'examinent et GitHub Actions exécute les tests. Le superviseur vérifie les résultats avant d'autoriser la suite.

Toutefois, une App très privilégiée représente également une cible sensible. Il faudrait isoler sa clé privée, limiter la durée et le périmètre des jetons, consigner les actions et surveiller les changements de permissions.

Les jetons d'installation GitHub App expirent au bout d'une heure et peuvent être générés avec un périmètre plus restreint que celui de l'installation. Il est donc possible de conserver des permissions déclarées étendues tout en émettant des jetons d'exécution plus limités.&#x20;

## 11. Déployer automatiquement des applications et administrer des serveurs

Votre GitHub App pourrait coordonner un pipeline complet allant d'un commit GitHub à une application déployée.

Elle peut notamment :

1. Détecter un changement sur une branche.
2. Déclencher une compilation.
3. Construire une image Docker par un workflow.
4. Exécuter des tests.
5. Publier une image dans un registre compatible.
6. Préparer un déploiement.
7. Déclencher le mécanisme d'installation sur un serveur.
8. Vérifier la disponibilité HTTP et les contrôles de santé.
9. Contrôler la version effectivement exécutée.
10. Publier un statut de déploiement.
11. Conserver les logs et les références de preuve.
12. Lancer une procédure de rollback prévue en cas d'échec.

Pour vos environnements VPS, Docker et Plesk, il faudra une passerelle d'infrastructure ou un runner correctement configuré.

GitHub ne fournit pas automatiquement l'autorisation d'administration d'un serveur externe. La GitHub App devient ici le contrôleur des opérations GitHub, tandis que l'exécution distante dépend de vos propres mécanismes d'authentification et de sécurité.

### Fonctions avancées envisageables

Vous pourriez automatiser des vérifications de synchronisation entre un commit GitHub et la version déployée, rechercher les divergences de configuration, examiner l'état de Docker, vérifier les déploiements sans régression et préparer des procédures de récupération.

Les déploiements de production pourraient conserver des validations humaines obligatoires tout en automatisant les étapes techniques.

## 12. Créer automatiquement de nouveaux projets

- Lancer les tests d'installation.

La création d'un dépôt à partir d'un template et la création de dépôts sont couvertes par des API GitHub, sous réserve des permissions appropriées.&#x20;

## 14. Aller encore plus loin avec une architecture événementielle

Je recommande de considérer les événements GitHub comme l'un des moteurs centraux du dispositif.

GitHub peut transmettre des événements à votre récepteur webhook. Votre plateforme peut ensuite les transformer en missions.

Quelques exemples :

| Événement reçu                 | Réaction envisageable                      |
| ------------------------------ | ------------------------------------------ |
| Nouvelle issue                 | Analyse et qualification automatiques      |
| PR ouverte                     | Lancement d'une revue indépendante         |
| Nouveau commit                 | Analyse des changements                    |
| Workflow échoué                | Création d'un diagnostic                   |
| PR fusionnée                   | Préparation de la suite du processus       |
| Alerte sécurité                | Ouverture d'une investigation              |
| Nouveau tag                    | Préparation d'une release                  |
| Déploiement en erreur          | Déclenchement du protocole d'incident      |
| Modification des permissions   | Réévaluation des capacités effectives      |
| Nouvelle installation de l'App | Inventaire et vérification du périmètre    |

Pour que le système soit fiable, le BUS devra gérer les événements répétés, la déduplication, les reprises sur erreur, les files d'attente, les délais, les priorités et la concurrence entre agents.

Votre architecture AUTO-INTAKE/BUS pourrait jouer un rôle central dans ce fonctionnement, sans dépendre des fonctionnalités d'agents Copilot.

## 15. Ce qu'une GitHub App ne peut pas faire seule

Même avec toutes les permissions disponibles, certaines limites demeurent.

| Capacité recherchée                           | Limite réelle                                                                  |
| --------------------------------------------- | ------------------------------------------------------------------------------ |
| Utiliser ChatGPT ou Claude                    | Nécessite une intégration ou un outil compatible avec le service IA            |
| Conserver toutes les conversations            | Nécessite un mécanisme de capture et de stockage                               |
| Raisonner de façon autonome                   | Nécessite un modèle IA ou un moteur de décision                                |
| Exécuter du code en permanence                | Nécessite un serveur, worker, runner ou service d'exécution                    |
| Lire des secrets en clair                     | Les API GitHub de secrets ne révèlent pas les valeurs enregistrées             |
| Accéder à tous les comptes GitHub             | Nécessite les installations et autorisations correspondantes                   |
| Ignorer toutes les protections                | Les règles GitHub restent applicables sauf exceptions explicitement autorisées |
| Contourner les limites API                    | Les limitations GitHub continuent à s'appliquer                                |
| Agir comme propriétaire de toute organisation | Le niveau de permission et le type d'identité restent déterminants             |
| Disposer gratuitement de toute ressource      | Les abonnements, quotas et coûts demeurent                                     |
| Modifier des serveurs externes                | Nécessite des identités et connecteurs spécifiques                             |
| Garantir une absence totale de régression     | Nécessite des contrôles, sans garantie absolue                                 |
| Garantir une exécution exactement une fois    | Nécessite un protocole applicatif de déduplication et de transaction           |

GitHub applique notamment des limites de débit REST et GraphQL, qui varient en fonction du type de jeton et des caractéristiques de l'installation.&#x20;

## 16. Faut-il une seule GitHub App ou plusieurs ?

Pour votre objectif, deux architectures sont envisageables.

### Option A — Une GitHub App universelle

Une seule App dispose d'une large couverture de permissions et s'installe sur tous les comptes qui l'autorisent.

Avantages : administration centralisée, identité technique unique, architecture plus simple et intégration homogène.

Inconvénients : concentration des privilèges, risques importants en cas de compromission de sa clé privée et nécessité de construire un mécanisme de délégation très robuste.

### Option B — Une App centrale et plusieurs Apps spécialisées

GITHUB APP CENTRALE

Découverte, orchestration, inventaire et coordination

App Code

Commits et PR

App Audit

Lecture et preuves

App CI/CD

Actions et déploiements

App Admin

Paramètres sensibles

App Security

Alertes et politiques

App Projects

Issues et planification

Cette deuxième architecture présente un avantage de sécurité : chaque App possède ses propres permissions, installations et identifiants.

Elle introduit cependant davantage de complexité opérationnelle, notamment pour coordonner les actions et auditer les différentes identités techniques.

Pour une plateforme ambitieuse, il serait pertinent de commencer par une identité centrale d'orchestration, accompagnée de capacités d'exécution séparées pour les fonctions les plus sensibles.

Cela n'empêche pas de constituer un catalogue général recensant toutes les permissions GitHub disponibles. Vous pouvez rechercher l'exhaustivité fonctionnelle sans concentrer toutes les clés et opérations dangereuses dans le même service.

## 18. Les possibilités les plus avancées

Avec les composants précédents, on peut envisager des fonctions encore plus évoluées.

Reconstruction historique automatique : parcourir les commits, issues, PR, commentaires et documents pour reconstituer la chronologie d'un projet, en conservant la distinction entre faits vérifiés, hypothèses et éléments introuvables.

Analyse des conséquences d'un changement : identifier les modules potentiellement affectés, les dépendances, les tests à exécuter et les équipes ou agents devant examiner la modification.

Détection des travaux concurrents : empêcher deux agents de modifier simultanément le même périmètre critique sans coordination.

Reprise après interruption : retrouver la dernière tâche validée, le checkpoint canonique, le commit de référence et les droits encore applicables, puis poursuivre la mission.

Planification par dépendances : créer un graphe reliant les tâches, les PR, les contrôles, les livrables et les étapes de production.

Supervision multi-comptes : piloter plusieurs installations GitHub App sans mélanger les règles de gouvernance de leurs propriétaires.

Contrôle anti-régression : comparer l'état logiciel avant et après modification, sur des critères techniques, fonctionnels, documentaires et opérationnels.

Audit de responsabilité : déterminer quel agent a proposé, réalisé, contrôlé et approuvé chaque opération, en distinguant systématiquement l'identité GitHub de l'identité de l'agent.

Découverte de capacités nouvelles : surveiller les évolutions de l'API GitHub et préparer l'activation gouvernée de nouvelles permissions ou fonctionnalités.

Migration inter-modèles : confier une mission commencée par Claude à ChatGPT, ou inversement, à partir d'un état persistant indépendant du fournisseur.

Ces fonctions ne sont pas toutes natives de GitHub, mais elles sont réalisables par combinaison de la GitHub App, des APIs, d'un stockage persistant et de votre moteur d'agents.

## 20. Le véritable potentiel pour votre objectif

Votre GitHub App peut être beaucoup plus qu'une connexion entre ChatGPT et GitHub.

Elle peut constituer la colonne vertébrale d'une plateforme de développement multi-agents, multi-projets, multi-comptes et multi-modèles, avec une mémoire persistante, un moteur d'exécution, des contrôles de gouvernance, une supervision et une capacité d'automatisation avancée.

Mais il est important de ne pas confondre trois ambitions différentes :

Exploiter toutes les permissions GitHub possibles signifie disposer de la plus large couverture technique que GitHub autorise.

Exploiter toutes les fonctionnalités GitHub possibles exige de développer les intégrations adaptées aux API, événements, produits et mécanismes d'exécution.

Construire une plateforme autonome ChatGPT/Claude nécessite, en plus, le système d'identités, de mémoire, de communication, de gouvernance et de supervision.

C'est en réunissant ces trois niveaux que vous pourrez tirer pleinement parti d'une GitHub App, sans utiliser Copilot.

Pour la suite, la décision architecturale essentielle sera de déterminer quelles capacités doivent être fournies directement par GitHub, lesquelles doivent appartenir à votre plateforme universelle et lesquelles doivent rester sous le contrôle de chaque projet. Cette séparation permettra de viser une couverture fonctionnelle maximale sans compromettre la continuité, la sécurité ou l'indépendance des différents dépôts.
